# ADR-002 — 存储选型：Parquet 列式为主存储，聚合立方为热层
> 日期：2026-08-02 | 状态：已接受 | 关联：fact_schema_v2.md, EVIDENCE.md

## 背景

架构优化目标：在"查询检索能力"与"数据库大小"间取得平衡。
候选方案：
- A: Parquet 列式（v2 定长编码）
- B: SQLite 定长表（行式 + B-tree 索引）
- C: 聚合立方（预计算 GROUP BY）

## 实测数据（10K 局 = 5,066,008 dahai 事件）

| 指标 | A: Parquet | B: SQLite | C: 立方 |
|------|-----------|-----------|---------|
| 存储大小 | **19.1 MB** | 595.6 MB | 0.007 MB |
| 相对大小 | 1x | **31.2x** | 0.0004x |
| Q1 立直巡目收支 | 68.1 ms | 332.6 ms | 21.6 ms |
| Q2 副露听牌率 | 9.2 ms | 1532.6 ms | 19.1 ms |
| Q3 摸切立直计数 | 4.9 ms | 574.4 ms | 15.7 ms |
| Q4 向听收支 | 92.7 ms | 2335.9 ms | 23.4 ms |
| Q5 局结局分布 | 10.6 ms | 1404.0 ms | 19.7 ms |
| 查询中位时延 | **10.6 ms** | 1404.0 ms | 19.7 ms |
| 全量加载 | 0.06 s | — | — |
| 构建耗时 | 167 s | 25.8 s(+输入) | — |

## 结论

**SQLite 行式在大小与时延上全面落败（31x 大小、100x 时延）**，原因：
1. 行式存储每行冗余重复字段（tile/turn/kyoku 等枚举值高度重复），无字典编码
2. B-tree 索引占用大且扫描慢；聚合需全列扫描
3. zstd + 字典/RLE（Parquet）对枚举值数据天然 30x 压缩

**Parquet 列式 + 立方热层胜出**：
- 查询时延：立方 16-23ms（预定义问题），Parquet 5-93ms（任意新问题）
- 空间：19.1MB/10K 局，扩展性与问题域适应能力最优

## 决策

1. **主存储：Parquet 列式（etl_v2 产物）** — 任意查询、新问题适应
2. **热层：聚合立方（cube_*.parquet）** — 高频预定义问题毫秒级
3. **弃用：SQLite 行式（tenhou_db.py 全量 states 路线不再扩展）**
4. **NL 层查询执行器改为 polars**（tenhou_nl.py 的 SQL 层对接 Parquet）

## 规模外推（899K 局全量）

| 指标 | 公式 | 值 |
|------|------|-----|
| dahai 事件 | 5,066,008 × 90 | ~4.56 亿 |
| Parquet 大小 | 19.1MB × 90 | **~1.7 GB** |
| 构建时间 (8进程) | 167s × 90 | ~4.2 小时 |
| 立方 | 忽略不计 | KB-MB |

## 遗留风险

- 点差/顺位查询（H 族）需 kyoku_scores 展开 —— 已含，验证中
- 大查询（全表 GROUP BY 数十维度）在 4.56 亿行上仍需分块 —— 待 50K 验证
- mjai 原始归档仍为权威源，ETL 可重跑（幂等）

## 关联

- 前置：fact_schema_v2.md（定长编码）、EVIDENCE.md（维度归纳）
- 后续：Phase 4 规模化（etl_v2 --limit 50000）

# ADR-003 — 天凤 XML 副露解码：权威 m 位布局（推翻低 2 位=类型假设）

> 日期：2026-08-03 | 状态：已接受（修复已上线并验证）| 关联：GAME_MODEL.md §2a, EVALUATION.md

## 背景

ETL 手牌追踪出现系统性偏差：暗杠行 98% consumed 移除失败（hs=12）、"暗杠牌从未进手"。
曾定性为"mjai 格式固有局限（副露后手牌恒少 1）"——**结论错误**。

## 根因

`tenhou_to_mjai.py _handle_n` 将 **m 低 2 位当作副露类型**（0=chi/1=pon/2=daiminkan/3=kan）。
实际 mjlog v4 布局（tehai.js / libriichi / pymahjong / Akagi 四实现一致）：

- 低 2 位 = **来源座位**（0 = 暗杠）
- bit2 = 吃、bit3 = 碰、bit4 = 加杠；无 flag = 大明杠（低 2 位≠0）/暗杠（=0）
- 碰/加杠的 bit5-6 是"未使用/新增副本号"，**不是拔北**（拔北 = 低 6 位 == 0x20）

后果：吃/碰被误判为暗杠/加杠，consumed 牌全错（如吃 2p-3p-4p → "暗杠 7m×4"）。

## 决策

1. `_handle_n` 按权威位布局重写（chi/pon/kakan/ankan/daiminkan 全部分支）
2. 牌解码：吃 `t=(M&0xFC00)>>10`（7 宽块展开）、碰/加杠 `t=(M&0xFE00)>>9`、杠 `hai0=(M&0xFF00)>>8`
3. 拔北判定用整 `(M & 0x3F) == 0x20`（仅查 bit5 会误伤碰）
4. ETL 补杠后岭上摸（just_kan）：杠后 dahai 若打的牌不在手牌 → 该牌即岭上摸的牌（天凤 XML 不发出岭上摸事件，规则要求杠后必摸）

## 验证

- 01e8ec31 局 2 golden test：碰 F + 碰 9s + 吃 2m-3m-4m → AGARI 手牌 5 张精确闭合
- 10K 重建：门清 100% hs=13、纯 chi/pon furo=1 100% hs=10、furo=2 100% hs=7、暗杠 100% hs=10
- 10 条不变量全部 PASS（此前 3 条 FAIL）

## 影响

- 旧 mjai（games/ 903K）与 v3_200k.parquet 含错误解码 → 需重转/重建（用户批准后）
- 旧转换器产物全部弃用；games_10k_fixed/ 为修复后权威重转

# ADR-004 — 天凤赤牌 ID 判定：`id % 4 == 0`（16/52/88），修复 `cp == 3` 错误

> 日期：2026-08-03 | 状态：已接受（修复已上线，全量重转待用户批准）| 关联：GAME_MODEL.md §2c, EVALUATION.md bug #10

## 背景

赤牌分析（切赤 5x 宣言立直）出现**反事实结果**：切赤 5m 宣言组手牌 5m≥1 占 49.8%（n=18,468），切普通 5m 组仅 30.8%（n=43,692）。

**牌理（用户铁律）**：赤 5x（0x）与普通 5x 牌效 100% 相同、仅多 1 番宝牌价值 → 手里同时有可切的 0x 与 5x 时**必切普通留赤** → 切 0x 宣言者手牌普通 5x 应**显著少于**切普通 5x 者。49.8% > 30.8% 方向完全颠倒，且"切赤者手里 5x≥1"占比极高，二者均违反牌理。

曾考虑的解释：故意切 0x 引挂（骗 3x/6x）——存在但极低概率，无法解释 +19pp 系统性偏差。

## 根因

`tenhou_to_mjai.py id_to_pai` 赤牌判定使用 **`cp == 3`**（`tile_id % 4 == 3` → ID 19/55/91 判赤）。

**权威依据**：kobalab/tenhou-log（天凤官方牌谱解析器，天鳳形式牌譜 → 電脳麻将形式）源码：

```js
// lib/convlog.js —— pai() 解码
if (type.hongpai && s != 'z' && n == 5 && pn % 4 == 0) n = 0;  // 赤牌 = pn % 4 == 0
```

即天凤赤牌 ID = **16/52/88**（`id % 4 == 0`，每类 5 号牌的第 1 张副本）。`cp == 3` 的 19/55/91 是**普通 5 的第 4 张**。

## 后果（标签系统性互换）

- 真赤（16/52/88）被输出为普通 5x → 归入"切普通"组
- 普通 5 第 4 张（19/55/91）被误输出为 5xr → 归入"切赤"组

**互换后两组数据反而全部符合牌理**：
- "切赤"组（实为切普通 ID 19）：手牌 5m≥1 达 49.8% —— 其中相当比例是**保留了真赤（ID 16）**，正是"切普通留赤"
- "切普通"组（混入切真赤 ID 16 的行）：真赤被当普通切出 → 手牌 5m 少 → 30.8%

**为何此前验证未发现**：赤/普通在 34 类别上同一位，手牌守恒/不变量验证均用归一化类别 → 标签互换不影响任何张数守恒，bug 长期潜伏。

## 决策

1. `id_to_pai` 赤判定：`cp == 3` → `cp == 0`（赤牌 ID = 16/52/88，即 `id % 4 == 0` 且类别 ∈ {4,13,22}）
2. 修复范围：`D:\tenhoulib\tenhou_to_mjai.py:42` 与 `D:\tenhoulib\tenhou-paifu-xml\converter\tenhou_to_mjai.py:35`（已确认无其他副本）
3. 全部赤牌相关分析（is_aka 列、dora_count 赤宝、切赤 vs 切普通差异、同色危险度）**结论需在重转重建后重估**

## 验证

- 函数级：ID 16/52/88 → 5mr/5pr/5sr，ID 19/55/91 → 普通 5（`id_to_pai(16, True)` = '5mr' 等 6 例）
- 端到端：300 个真实 XML 重转，143,859 次摸牌事件，3,173 张赤牌 **0 失配**（`verify_aka300.py`：XML 原始 ID vs 转换器输出逐一对齐）
- 500 文件试转全部成功（`games_200k_aka_fixed/`）

## 影响

- **所有基于 is_aka 的既有分析结论失效**（aka_riichi_analysis / aka_suit_analysis / aka_vs_plain5 / b3_queries PY2 等）
- v3_200k.parquet 含错误赤标记 → 需重转 200K + ETL 重建 + invariant 验收（用户批准后）
- games_200k_aka_fixed/ 已含 500 文件修复后重转（试转产物）

# ADR-005 — 数据纯净性原则：局级准入（kyoku 全动作合法才入库）

> 日期：2026-08-03 | 状态：已接受 | 关联：GAME_MODEL.md §4, AUDIT_TILE_ID.md §3b, EVALUATION.md §四c

## 背景

牌 ID 全面审计（AUDIT_TILE_ID.md）发现两个数据格式层面的固有限制：

1. **副露 consumed 副本歧义**：天凤 `<N m="...">` 只编码类别（+被叫位置+赤显示标志），**不编码具体副本 ID（0-135）**。手牌有多张同类别牌时，无法确定玩家吃/碰用哪张 → AGARI 交叉验证不一致 **3.81%**（171/4,493）
2. **副露赤牌 ID 不可恢复**：m 字段"副本位 0=赤"标志与实际赤牌 ID 83% 不符

面对"部分局无法 100% 还原"的现实，需决策数据质量策略。

## 决策

**局级准入——数据纯净性优先于数据量**：

1. 一个小局（kyoku）**全部动作合法**才入库；任何局部不确定/违规 → **整局丢弃**
2. 准入条件 G-1..G-4：副露移除成功 / dahai 移除成功 / AGARI 交叉验证一致 / INV-1..10 满足
3. **不降级入库**：信息论极限（副本歧义）导致的 AGARI 不一致局**直接拒绝**，不以"部分正确"入库
4. 丢弃不静默：ETL 记录丢弃原因与计数，可审计；原始 XML 保留（games/ 权威源）
5. **所有分析基于纯净局子集**（样本量 = 纯净局），保证结论可复现、可追溯

## 验证

- 按类别移除（Plan A）：副露移除 100% 成功；AGARI 交叉验证一致率 96.19%（4,322/4,493）
- 剩余 3.81%（171 例）100% 归因为副本歧义（192 个 ev extra 牌全部属于副露过的类别，0 例其他原因）
- 纯净性原则下：这些局整局丢弃 → 入库数据 100% 通过 AGARI 交叉验证

## 影响

- 转换器 `_handle_n` 需修复：按类别移除（不再推导 ID）
- ETL 需实现局级准入过滤 + 丢弃审计日志
- v3_10k / v3_200k 重建时应用纯净性原则（样本量以纯净局计）
- 历史文档已更新：GAME_MODEL.md §4（准入条件）、EVALUATION.md §四c（原则）、AUDIT_TILE_ID.md §3b（归因）

# ADR-006 — 重建门禁流水线 + 统计基准 + 内存护栏

> 日期：2026-08-04 | 状态：已接受（已实现并验证）| 关联：STATS_BASELINE.md, verify_gate.py, mem_guard.py, stats_sanity.py

## 背景

历轮教训：**全量重建 200K（~2.5 小时）后才发现 bug → 全部作废**（赤牌 ID bug 一次；1 亿行 OOM 强制关机三次 Kernel-Power 41）。需要系统性防线：把 bug 拦截在"修改后、全量前"，并杜绝长任务 OOM。

## 决策

### 1. 重建门禁流水线（verify_gate.py，L0-L3 全过才允许 L4 全量）

| 层 | 内容 | 耗时 | 拦截 |
|----|------|------|------|
| L0 | converter_anchor_test（8 锚点 + 赤牌/副本 golden）| <1s | 函数级错误 |
| L1 | 黄金样本集 200（AGARI 逐张一致 + meld 移除 100%）| ~1min | 稀有场景（国士/抢杠/双和/流局类型/赤牌副露/长局/BYE）|
| L2 | invariant（sample 截断）+ regression 15 项 | ~5min | 常规 bug |
| L3 | stats_sanity（nodocchi 基准 p10-p90）| ~6min | 统计偏差 |

判定：L1 meld 移除失败必须 0（硬）+ AGARI 一致率 ≥95%（信息论极限 3.8% 不计 FAIL）；L2/L3 全 PASS；L3 WARN 允许人工复核。

### 2. 统计基准（STATS_BASELINE.md）

- 数据源：nodocchi Phoenix DB（270 玩家 / 2000 万局聚合，min=5000）
- 用途：stats_sanity.py 阈值（p10-p90 PASS + ±2σ 告警）
- 关键锚点：赤宝率 49.8%（赤牌修复正确性验证）
- 局限：凤凰卓强者池，允许 ±1-2pp 段位差

### 3. 内存护栏（mem_guard.py）

三层防护（16GB 机器 OOM 教训）：
1. **preflight**：运行前估算（parquet 大小×膨胀系数）超限 → 拒绝
2. **MemoryWatchdog**：运行中轮询 RSS + 系统可用，超限 → abort
3. **guard_child**：子进程 RSS >4GB 或系统可用 <2GB → kill

配套修复：polars 1.40 `streaming=True` 弃用 → `engine="streaming"`；invariant/stats_sanity 加 `--sample`（limit 截断防物化）——实测 invariant 全量 8.2GB → 500 万行截断 1.1GB。

### 4. 纯净性原则落地（ADR-005 实现）

- 转换器 `_handle_n` 副露**按类别移除**（m 字段只编码类别不编码副本 ID；推导 ID 移除 31.8% 失败 → 0）
- ETL 局级准入：dahai/副露移除失败 → 整局丢弃 + `_DROP_STATS` 审计（实测 200 文件丢弃 0.73% 局）

## 验证

- L0 8/8 PASS；L1 AGARI 95.58% + meld 移除 0 失败；L2 invariant+regression 全 PASS（2M 行）；L3 统计 4 PASS + 1 WARN（和率 21.1% vs 21.4-22.7%，段位差）
- 内存护栏：preflight 拒绝过（可用不足）、子进程 RSS 拦截过（8.2GB→kill）、系统可用兜底过——三层均实测生效
- 转换器修复：2000 文件 18,031 和牌，meld 移除失败 0；ETL 局级准入后不变量 0 违反

## 影响

- 所有长任务必须带护栏运行（verify_gate 已内置；独立脚本用 mem_guard）
- 全量重建流程：修复 → L0-L3 门禁 → L4 全量（invariant/stats 用 sample，全量验收单独跑）
- 新文档：STATS_BASELINE.md（基准）、mem_guard.py（护栏）、verify_gate.py（门禁）
